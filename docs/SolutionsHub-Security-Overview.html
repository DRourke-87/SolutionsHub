SolutionsHub Security Overview

A web application that captures new Amentum Solutions and Offerings, routes them through review and approval, and publishes the approved result. This note describes the architecture, the data it holds and how people sign in — prepared for IT and Cyber review.

01 What we are asking you to review

SolutionsHub replaces a Microsoft Form plus manual email chasing with a single tracked process, from submission through review, approval and publication.

It is built entirely from Azure platform services in one resource group, and holds internal business content about Amentum offerings plus the work contact details of the people who own them. It stores no passwords and processes no payment data.

Two design decisions need your explicit agreement, and both are set out in full below: the application is reachable from the public internet with access controlled by identity rather than network location (#05), and it authenticates people by emailing a one-time link to an Amentum mailbox rather than through corporate SSO (#05), because its users sit across two unconnected domains.

Quick answers

Who can sign in?

Only holders of an @amentum.com, @global.amentum.com or @amentumcms.com mailbox. No other address can obtain access.

Where does the data live?

One Azure resource group in a single region. Nothing leaves Azure except outbound notification email.

Are passwords stored?

No. The service is passwordless, so there are no password hashes to breach or reset.

Is there an audit trail?

Yes. Every sign-in, approval and status change is written to an append-only table with actor, timestamp and source IP.

Third parties involved?

Microsoft Azure only, plus GitHub for source control and deployment. No other processor.

Is data encrypted?

TLS 1.2+ in transit everywhere; Azure platform encryption at rest on the database and file storage.

What is the blast radius?

Internal marketing and capability content, plus names and work email addresses. No customer, classified or personal-sensitive data.

Can access be revoked?

Immediately. An administrator disables the account, which kills every active session and blocks new sign-in links.

02 Architecture

Five managed Azure services in one resource group. There are no virtual machines to patch, no containers to maintain and no inbound connections from anywhere other than a user's browser.

Azure serviceRole in the solutionSecurity posture
App ServiceLinux, Python, B1 plan Hosts the web application. The only component users reach. HTTPS enforced, TLS 1.2 minimum, FTP disabled, HSTS and a strict Content Security Policy on every response.
PostgreSQLFlexible Server, Burstable Submissions, role assignments, comments and the audit trail. TLS required on every connection. Reachable only from Azure services, not the public internet. Point-in-time restore for 7 days.
Blob StorageStorageV2, LRS Files attached to a submission. Private container, anonymous access disabled. Files are served only through the application after a permission check. Soft delete 30 days, versioning on.

Application Insightson Log Analytics Errors, performance and availability monitoring. Retained 30 days with a daily ingestion cap. Email addresses are kept in the audit table, not in telemetry.

Deployment

All infrastructure is defined as code (Azure Bicep) and deployed from GitHub Actions, so the running configuration is reviewable and reproducible. Lint, tests and a database migration check run on every change before it can deploy.

03 Data flow

A submission moves through seven stages — Submitted, Under Review, Updates Required, Awaiting Approval, Approved, Ready to Publish, Published. Each transition is checked against the user's role, written to the audit trail, and triggers an email to whoever owns the next action.

Data enters in one place, through the intake form. It leaves in two: notification email to Amentum mailboxes, and an export package the publishing team downloads when content is approved for publication.

Proposed usage boundary

SolutionsHub is intended for internal business and marketing content. We propose it is not approved for classified, export-controlled (ITAR/EAR) or personal-sensitive material, and that this is stated to users at the point of upload. We would welcome your wording.

The only personal data held is business contact information for Amentum employees, processed on legitimate interest for internal business administration. There is no special-category data and no customer personal data.

04 Why not corporate SSO

The intended users sit across two unconnected domains, so no single Entra ID tenant contains all of them. Federating the two is a much larger piece of work than this application justifies.

What both populations do share is an Amentum mailbox. The service therefore treats control of an Amentum mailbox as the proof of identity, which is the same assumption behind every corporate password-reset flow. If SSO becomes available across both domains, it can replace this mechanism without changing anything else in the design.

05 How sign-in works

There is no password. A user enters their work email, receives a one-time link, and confirms on the page that link opens.

Controls at each stage

ControlSetting
Accepted sendersThree Amentum domains only. Any other address receives an identical response and no email, so the form cannot be used to discover valid addresses.
Token strength32 bytes from the operating system's cryptographic random source.
Token at restOnly a SHA-256 hash is stored. A database compromise yields no usable links.
Token lifetime15 minutes, single use, invalidated when a newer link is requested.
Request throttling5 link requests per address per hour, 30 per source network, 10 failed confirmations per network.
Session cookieSigned, HttpOnly, Secure, SameSite=Lax. Server-side record so it can be revoked.
Session lifetime8 hours sliding, 24 hours absolute. Optional 30-day trusted device.
RevocationDisabling a user kills all their sessions immediately and blocks new links.

Why the endpoint is public

Users on two unconnected domains, working from offices, home and client sites, cannot reliably share a single network path. Rather than depend on network location, the design places the control at identity.

Only four things are reachable without a session: the sign-in form, the link confirmation page, a health check that returns nothing but ok, and static CSS and images. Every other URL redirects to sign-in. An attacker who reaches the site without an Amentum mailbox can do exactly one thing — cause a sign-in email to be sent to an Amentum address, which is rate limited as above.

If you would prefer defence in depth, IP restrictions or Azure Front Door with WAF can be layered on top without any application change. We are happy to be directed here.

06 Who can do what

Signing in proves identity; it grants no privilege beyond submitting an offering and viewing approved content. Roles are held in the application and assigned by an administrator. Every check runs server-side on every request.

RoleCan doAssigned by
Signed-in userSubmit an offering, browse approved content, edit their own submission before review.Automatic on first sign-in
ReviewerValidate submissions and request changes, optionally scoped to one business group.Administrator
ApproverApprove or reject. Cannot approve an offering they own.Administrator
PublisherPrepare approved content and record publication.Administrator
AdministratorManage roles and reference data, disable users, read the audit log.Existing administrator
  • Separation of duties — nobody can approve their own offering, administrators included.
  • No self-elevation — a user cannot grant themselves a role; both parties are named in the audit record.
  • First administrator is set by configuration and only applies while no administrator exists.

08 Known gaps and decisions taken

Stated plainly so you are not asked to discover them. The first three are consequences of the current development-phase permissions and are already scheduled.

ItemPositionStatus
Secrets in configuration Service credentials sit in App Service configuration, encrypted at rest and visible only to those with write access to the app. Azure Key Vault was not used because creating the role assignments it needs requires permissions the project does not yet hold. Planned
Service-to-service authentication Components authenticate with keys and connection strings rather than managed identity, for the same permissions reason. No credential is in source control. Planned
Sender domain Email currently sends from an Azure-managed domain. A verified Amentum subdomain with SPF, DKIM and DMARC is required before pilot, both for deliverability and so recipients can see the mail is genuinely ours. Before pilot
Database network exposure The database accepts connections from Azure services and enforces TLS with a generated credential. Restricting to the application's outbound addresses, or private networking, is the hardening step. Planned
Public endpoint A deliberate decision, reasoned in #05. Reversible without application changes. Decision
Email as identity proof A deliberate decision, reasoned in #04. Anyone controlling an Amentum mailbox can sign in — the same assumption as corporate password reset. Decision
No high availability Single instance, single region. This is an internal productivity tool, not a service with an availability commitment. Accepted

09 What we need from you

  • Agreement on the two design decisions in #05 and #04 — the public endpoint and email-based identity — or direction to change them.
  • Confirmation of the usage boundary in #03, and your preferred wording to show users at upload.
  • A DNS record change to create a verified sending subdomain, so notification email is demonstrably from Amentum. We can supply the exact records; no change to any existing domain is required.
  • Any additional logging, retention or review requirements you need before pilot.
